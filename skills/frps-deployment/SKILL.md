# 内网穿透部署指南

本技能用于编排现有 API，完成 VPS 侧内网穿透服务端部署、路由器侧内网穿透客户端配置以及最终验证。

默认工作流拆分为 4 个阶段：

1. 状态获取
2. 服务端部署
3. 客户端部署
4. 成功验证

## 使用原则

1. 普通用户默认进入“四阶段主流程”；只有在用户明确说“只看状态”“只重置”“只配客户端”“只验证”时，才进入模块模式。
2. 每一步都以工具返回结果决定下一步，不猜测 VPS、路由器或服务状态。
3. 只要存在专用 API，就必须优先调用专用 API，不允许用自然语言推断代替接口职责。
4. 服务端产出的监听端口、认证密钥和公网地址，是后续客户端部署的唯一可信来源（即来自 `openclaw_get_frps_status` 等接口的真实服务端数据）。
5. 若发现旧客户端配置与当前服务端参数不一致，必须无条件以服务端当前状态覆盖旧配置，**绝对不允许沿用 `clawwrt_get_xfrpc_common_config` 获取到的旧客户端参数**进行后续配置。
6. 认证密钥必须直接复用 `openclaw_get_frps_status` 的回读结果，不允许模型自行生成、猜测或要求用户手工补写。

## 通用规则

1. 涉及任何内网穿透请求时，第一步必须调用 `openclaw_get_frps_status`。
2. 在状态获取完成前，不得询问用户任何客户端参数。
3. 若状态判断需要部署或修复服务端，在服务端部署完成前，不得询问 `device_id`、本地 IP、本地端口、远端端口等客户端参数。
4. `token` 必须始终非空；若服务端返回空值，必须重新部署并显式注入随机字符串。用户主动提供 token 时，才使用用户值。
5. `server_addr` 优先通过 `openclaw_get_vps_public_ip` 获取，再由用户确认是否直接使用该公网 IP 或改用自定义域名。
6. 面向用户的输出中，不使用 `FRPS`、`frps`、`frpc`、`xfrpc` 等技术代号；统一使用“内网穿透服务端”“内网穿透客户端”“认证密钥”等表达。
7. 需要用户输入参数时，必须逐项询问，并附一句用途或填写建议；不允许只抛出参数名。
8. 任一步失败且没有明确恢复路径时，立即停止并报告失败模块、失败步骤、API 名称和关键错误信息。

## 默认入口：四阶段主流程

当用户表达“配置内网穿透”“把路由器映射到公网”“远程访问路由器内网服务”等意图时，直接进入以下流程：

1. 执行 `references/status.md`
   - 先判断 VPS 侧是否已安装并运行内网穿透服务端。
   - 必须盘点并向用户全面展示所有设备的客户端配置现状。
   - 这一阶段只做状态获取和路径分流，不采集用户的新配置参数。
2. 执行 `references/server-deploy.md`
   - 若服务端未安装、未运行或认证密钥为空，立即部署或修复。
   - 本阶段只负责把服务端恢复到可用状态；认证密钥仍以 `references/status.md` 里真实回读到的结果为准。
3. 执行 `references/client-deploy.md`
   - 选择目标设备。
   - 配置客户端公共连接参数。
   - 创建需要暴露到公网的 TCP 映射。
4. 执行 `references/verify.md`
   - 先检查远端端口监听状态，再引导用户做实际访问测试，不能把监听出现直接当成最终成功。
   - 必要时重启客户端后重试一次。
   - 引导用户完成实际访问验证。

说明：四阶段顺序固定。状态获取负责“决定是否需要安装服务端”；服务端部署只做 VPS 侧工作；客户端部署只做路由器侧工作；成功验证只做结果确认与失败定位。

## 模块模式

当用户明确要求单独执行某一部分时，只读取对应 reference：

1. 查看当前内网穿透状态：读 `references/status.md`
2. 部署或修复 VPS 服务端：读 `references/server-deploy.md`
3. 配置路由器客户端：读 `references/client-deploy.md`
4. 验证当前配置是否成功：读 `references/verify.md`
5. 重置已有配置：读 `references/reset.md`

若用户一次提出多个目标，按用户表述顺序逐项执行；每完成一个模块，再进入下一个模块。

## 关键输入规则

1. 只要涉及路由器客户端配置，必须先调用 `clawwrt_list_devices` 获取在线设备，再让用户明确确认目标 `device_id`。
2. 未确认 `device_id` 时，不允许默认操作所有在线设备。
3. 本地 IP 地址、本地端口、远端端口都必须由用户明确提供；禁止猜测或自动补全。
4. `server_addr` 不能为空，且不能使用 `localhost`、`127.0.0.1`、`0.0.0.0` 之类明显错误的值。
5. 本地端口和远端端口必须是 `1-65535` 的整数；远端端口不能与服务端监听端口冲突。
6. 若同一设备已有相同远端端口映射，必须先提示冲突，再要求用户改端口。
7. 若用户要求清理、禁用或删除某条映射，必须使用对应的客户端管理 API，不得把“删除单条映射”和“清空全部映射”混为一个动作。
8. 配置客户端公共连接参数时，`clawwrt_set_xfrpc_common` 必须一次性写入 `server_addr`、`server_port`、`token` 三项；禁止只更新 `enabled` 或任一单字段。

## 推荐执行形态

1. 入口阶段先调用 `openclaw_get_frps_status` 判断服务端，接着必须调用设备和映射相关 API 盘点所有现有配置；不要一开始就追问新的映射参数。
2. 服务端部署成功后，优先复用 `openclaw_get_frps_status` 和 `openclaw_get_vps_public_ip` 的返回值，不要让用户重复提供监听端口、认证密钥或公网 IP。
3. 客户端部署时，先设置公共连接参数，再创建单条或多条服务映射；其中 `token` 必须沿用状态盘点阶段回读到的值。
4. 公共连接参数属于全量覆盖写入语义；若只传部分字段，可能导致历史字段被清空，因此必须传完整参数集。
5. 验证阶段先做机器可判定的监听检查，再让用户做实际访问测试。
6. 重置流程不是四阶段主线的一部分；仅在用户明确要求重置或修复旧配置时，进入 `references/reset.md`。

## 共通错误输出

每次错误至少包含：

1. 失败模块
2. 失败步骤名
3. 调用的 API 名称
4. 错误原文或关键字段
5. 已完成步骤与未执行步骤
6. 建议用户选择：重试、回滚、或人工介入
